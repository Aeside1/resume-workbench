# ADR 010: 自适应与弹性布局（推翻「第一阶段仅面向桌面宽屏」）

- **状态（Status）**：Accepted（已确认）
- **日期（Date）**：2026-10-25
- **决策者（Deciders）**：用户 & AI Pair
- **关联文档**：[ADR 001](001-ui-redesign-workbench-and-focus-canvas.md)（§2.3 被本 ADR 取代）、[ADR 005](005-resume-plan-reference-model-and-archive-boundary.md)、[ADR 007](007-focus-expands-in-content-area.md)、[PRD.md](../PRD.md)、[CONTEXT.md](../CONTEXT.md)

## 1. 背景与问题陈述（Context）

[ADR 001](001-ui-redesign-workbench-and-focus-canvas.md) §2.3 把平台定位写成：

> **平台定位**：第一阶段仅面向**电脑桌面端宽屏**（1080p / 2K / 4K），优先做好大屏下的舒适居中画布排版，避免在初始阶段过早陷入复杂的移动端自适应。

这条口径在原型期是合理的（先把领域模型与内容闭环跑通），但布局实现把它固化了：侧栏固定 240px、卡片操作排实测 252px 且永不压缩、方案历史版本固定 300px、正文大标题不换行。真实 Edge + `/api` 打桩实测（`main` @ `4676766`，issue #19 票面）结果是：

| 窗口宽 | 经历列表 | 经历画布正文 | 方案编辑器正文 | 方案编辑器 + 历史版本 |
|---|---|---|---|---|
| 390（手机竖屏） | 左右要滑 326 | 左右要滑 61 | 左右要滑 49 | 左右要滑 186 |
| 768（平板 / 横屏） | 不滑 | **162** | **166** | 正文被压到 166 |
| 1024（笔记本拖窄） | 不滑 | **403** | **407** | 正文被压到 407 |
| 1440 | 不滑 | 794 | 798 | 798 |

用户对这件事的原话是：

> 添加一个 issue，移动端页面显示适配，现在的工作台界面在移动端排版显示糟糕
>
> 不只是移动端适配，这个 issue 应该还要负责 flexible 的工作

也就是说，要的不只是「手机上能打开」，而是**布局能随可用宽度弹性让位**：窗口拖窄、平板竖屏、手机竖屏都要能读能改。

## 2. 决策要点（Decisions）

### 2.1 推翻 ADR 001 §2.3：支持三档尺寸，1440 以上保持现状

| 档位 | 代表宽度 | 必须做到 |
|---|---|---|
| 手机竖屏 | 390 | 能看、能改正文、能挑简历亮点；不左右滑 |
| 手机横屏 / 平板竖屏 | 768 | 同上，且画布与方案编辑器都可用 |
| 笔记本窗口拖窄 | 1024 | 同上，双栏按「内容区还剩多少」让位 |
| 桌面 | ≥1280（1440 为基准） | 保持原有排版，不回退 |

**明确不做**（不让「适配」无限膨胀）：

- 手机上的「展开专注」不承诺 —— 它为大屏长时间写作设计，窄屏只须能用画布写作；
- 手机横屏不单独适配，只保证不横滑；
- 不为了手机另做一套页面结构（见 §2.2 的判据与 §2.6 的唯一例外）。

### 2.2 宽度分界只剩三条：640 / 1024 / 1280

| 线 | 含义 | 谁用 |
|---|---|---|
| 1280 | 窗口不足 1280（不是内容区） | 左侧导航自动收成 76px 图标条 |
| 1024 | 内容区 / 窗口不足 1024 | 画布大纲与方案历史版本让位；触控尺寸放大 |
| 640 | 窗口不足 640 → 侧栏不占位（顶部条 + 滑出面板）；内容区不足 640 → 单列、字号降一档、卡片上出现上下移按钮 | 壳层与内容区 |

只有这三条：侧栏的两条用窗口宽度（`1279` / `640`，即两条线的边界），内容区用容器宽度（`1024` / `640`）。

**存量例外（待统一，不在本票范围）**：本次改动新增与改过的断点只用这三条；仓里还有几个更早的页面带着旧断点——`auth-page.css`（960 / 560）、`workbench-view.css` 与 `forms.css`（720 / 520）、`guest-mode.css`（79）——它们不属于本票要改的七个块，留作后续统一项（票面也把「靠注释 + 审查保证统一」写成了显式兑付方式）。

CSS 的媒体查询条件不能写成变量，所以统一性靠「每个样式文件头注释写明本条线的口径 + 代码审查 + `responsive.e2e.mjs` 四档取证」保证；将来若把布局迁到 Tailwind，把这三条写进配置即天然集中。

### 2.3 判据分两类：壳层按窗口，内容区按容器

ADR 001 之后的所有布局都是「侧栏 + 内容区」。同一个窗口宽度下，内容区宽度取决于侧栏是否收成图标条，所以**判断依据必须是「内容区还剩多少」**，不能一律用窗口宽度：

- **壳层（侧栏 / 窄屏顶部条）用窗口媒体查询**。侧栏是内容区的兄弟节点，CSS 里量不到兄弟的宽度；1280 与 640 两条线都是壳层自身的拓扑变化。
- **内容区里的栏位让位用容器查询**（`@container content (...)`）。各功能块根节点声明 `container-type: inline-size; container-name: content`：
  | 容器 | 覆盖的让位规则 |
  |---|---|
  | `.experience-hub-panel` / `.plan-hub-panel` | 两个列表页的栅格、标题区、操作条 |
  | `.focus-canvas-wrapper` | 画布双栏（大纲栏落位）、卡片头与操作排 |
  | `.plan-editor-body` | 方案条目行、块头、文稿预览 |

**为什么容器不放在 `.app-main` 上**：`container-type: inline-size` 隐含 `contain: layout`，会让容器内的 `position: fixed` 相对**容器**定位而不是视口。方案历史版本在窄屏要变成从右侧滑出的浮层，必须相对视口；所以容器只能放在功能块根节点上，让那个浮层面板留在容器外（它是 `.plan-editor-body` 的兄弟节点）。同一原因，**一切需要相对视口浮出的层（滑出导航面板、弹窗、抽屉、历史版本浮层）都用窗口媒体查询**。

### 2.4 各栏让位规则

| 栏位 | 让位条件 | 让位方式 |
|---|---|---|
| 左侧导航 | 窗口 < 1280 | 收成 76px 图标条（文本节点不渲染，可访问名走 `aria-label`；折叠开关在这一档不渲染——形态是强制的，不造死按钮） |
| 左侧导航 | 窗口 ≤ 640 | 不占位，改为顶部条菜单按钮 + 从左侧滑出的面板；点导航项 / 关闭按钮 / Esc / 遮罩收起 |
| 经历画布右侧大纲 | 内容区 < 1024 | 插到「经历概况」与「具体工作内容」**之间**（不落到整页底部：大纲是导航，滚到底才用得上）。实现上由 `ResizeObserver` 量容器宽度切换，仍按内容区而不是窗口宽度判 |
| 方案编辑器右侧历史版本 | 窗口 ≤ 1024 | 从右侧滑出的浮层（内容区判据做不到，理由见 §2.3） |
| 卡片栅格（两个列表页） | 容器 < 320 起自动单列 | `repeat(auto-fill, minmax(min(320px, 100%), 1fr))` |
| 工作项卡片操作排 | 内容区 < 1024 换行；< 640 竖排 | 标题与操作不再抢一行 |
| 工作项卡片的排序按钮 | 内容区 < 640 | 出现「上移 / 下移」；桌面保留拖拽与方向键 |
| 正文列 | 任何宽度 | 不小于 320（低于即按上表让位，不压缩） |
| 工作台概览 / 两个列表页的宽度 | 任何宽度 | 铺满内容区：旧值封顶 1400px，在 2560 这类宽屏上右侧会留一大片空白；栅格自己按可用宽分列 |

### 2.5 手指可用性与页面高度

- **触控目标 ≥ 44×44**（WCAG 2.5.5）：窗口 ≤ 1024 时对 `button` / `[role=button]` / `[role=switch]` / `[role=tab]` 与表单字段设最小尺寸；只提尺寸，不动颜色、圆角、字体（AGENTS.md 第 3 条），1440 桌面保留框架默认紧凑密度。
- **不靠悬停才能发现功能**：窄屏（≤1024）一律常显「改名铅笔」这类原本 `opacity: 0` 的悬停装饰。
- **拖拽排序在手机上由按钮替代**：内容区 < 640 时每张工作项卡片渲染「上移 / 下移」两个图标按钮（首项禁用上移、末项禁用下移），桌面**保留** framer-motion 指针拖拽与手柄方向键，`scripts/reorder.e2e.mjs` 继续作为拖拽的唯一证伪手段。
- **页面高度用动态视口单位**：`min-height` / 专注态高度从整屏 `vh` 改为 `dvh`；`index.html` 的 viewport 加 `interactive-widget=resizes-content`（软键盘弹起时布局视口跟着缩）与 `viewport-fit=cover`（刘海屏安全区），底部留白叠 `env(safe-area-inset-bottom)`。
- **抽屉宽度**：`.resume-drawer-panel` 本来就是 `width: 480px; max-width: 100vw`，窄屏会跟着视口收缩，所以**不改它的宽度**（改宽会连带把 1440 的抽屉从 480 缩成 384，反而违反「1440 保持现状」）。本票真正修的是版本行不换行与面板内边距。

### 2.6 改法以小改为主，结构只动一处

除左侧导航改成「点按钮滑出的面板」（`AppShell.tsx` + `styles/layout/topbar.css` 的窄屏顶部条）外，其余全部是样式表内「窄了就换个样子」。唯一另一处组件改动是**新增**上下移按钮的渲染（`WorkContentBlock.tsx` / `FocusCanvasDocument.tsx`），它是 §2.5 手指可达性的必要件，不改变既有结构。

**不影响 HeroUI**：不写 `!important`，不覆盖框架的视觉变体；布局钩子只用公开的 `data-slot`（沿用 `topbar.css` 既有做法）与框架的语义变量（`--backdrop` / `--overlay-shadow` / `--surface` 等）。

### 2.7 自动取证：`scripts/responsive.e2e.mjs`

本票的验收断言的是**真实排版结果**，jsdom 量不出来，所以固定关卡新增一条真浏览器探针：390 / 768 / 1024 / 1440 四档，各跑「经历列表 → 新建经历弹窗 → 经历画布（含亮点抽屉）→ 简历方案列表 → 方案编辑器（含历史版本面板）→ 文稿预览」，逐档断言：

1. **不左右滑**：`documentElement.scrollWidth ≤ clientWidth`（票面写的是 `scrollWidth === innerWidth`；`clientWidth` 不含滚动条占位，是更严的等价形式，且在无经典滚动条时二者就是同一个数），失败时打印越界元素；
2. 画布正文列 ≥ 320；
3. 工作项卡片 / 版本行 / 条目行 / 预览的内容宽度不超出自身（长 URL 断行）；
4. 内容区 < 640 时上下移按钮可见、≥ 44×44、点一下顺序真的翻转且排序请求带完整新顺序；内容区 ≥ 640 时不显示（判据与 CSS 同源：读容器内容盒宽度，不用窗口宽度近似）；
4′. 内容区 < 1024 时大纲插在「经历概况」与「具体工作内容」之间（页内 `top` 递增），且不再渲染右侧伴随栏；宽屏反过来；
5. 触控目标（按钮 / `role=button` / 开关 / Tab / 表单字段）在 390 / 768 / 1024 三档都 ≥ 44×44，且覆盖打开抽屉与打开弹窗这两种状态（按钮两个维度都量，表单字段只量高度）；
6. 弹窗（新建经历分组）在四档都不越界、页面不横滑；窄屏铅笔图标常显；画布底部按钮滚到底够得到。

探针在本地 `RESPONSIVE_ARTIFACTS` 留每档截图，固定关卡跑 `npm run test:responsive:e2e`（见 README 的关卡矩阵）。

## 3. 结果（Consequences）

### 3.1 实测（同一台机器、真 Edge、`/api` 打桩，`responsive.e2e.mjs`）

| 窗口宽 | 经历列表 | 弹窗 | 亮点抽屉 | 方案编辑器 | 历史版本面板 | 文稿预览 | 正文列 |
|---|---|---|---|---|---|---|---|
| 390 | 390 = 390 | 390 = 390 | 390 = 390 | 390 = 390 | 390 = 390 | 390 = 390 | 342 |
| 768 | 768 = 768 | 768 = 768 | 768 = 768 | 768 = 768 | 768 = 768 | 768 = 768 | 598 |
| 1024 | 1024 = 1024 | 1024 = 1024 | 1024 = 1024 | 1024 = 1024 | 1024 = 1024 | 1024 = 1024 | 839 |
| 1440 | 1440 = 1440 | 1440 = 1440 | 1440 = 1440 | 1440 = 1440 | 1440 = 1440 | 1440 = 1440 | 794 |

（每格是 `documentElement.scrollWidth = clientWidth`（无经典滚动条时也等于 `innerWidth`）；正文列是 `.focus-canvas-main-col` 的实测宽度，四档都 ≥ 320。）

对比 ADR 上一版（票面基线）：390 的手机列表从「左右要滑 326」变成 0；768 / 1024 的画布与方案正文从 162 / 403 变成整宽可读；方案编辑器开历史版本不再把正文压到 166。

### 3.2 代价与边界

- 容器查询与媒体查询**分工并存**，读样式的人必须先看文件头注释才知道该用哪条线；这是 `contain: layout` 带来的硬约束，不是风格选择。
- 侧栏在 1280 以下**强制**图标条，用户无法在窄窗里展开成带文字的侧栏（要文字就把窗口拉宽，或用 ≤640 的滑出面板）；因此折叠开关在这一档不渲染，持久化的折叠偏好也只在 ≥1280 生效。
- 窗口 ≤1024 的 44×44 规则是**一把粗粒度的刀**（对所有 `button` / `[role=*]` / 表单字段生效），密级工具栏（如富文本工具栏）在这一档会变高变宽；取舍是「手指能点中」优先，且与框架视觉无关（只动尺寸）。
- 容器查询按内容盒计算，`640` 在 768 窗口的实际命中点是内容区（约 598），即「768 档」在排版口径上归入窄屏档；这是有意的（正文列 598 时按窄屏排版更好读）。
- 历史版本浮层没有遮罩（保持 ADR 005 §2.5 的「非模态」口径），收起靠面板自带按钮与页头开关。
- `contain: layout` 会让容器内的 `position: fixed` 相对容器定位。今天不受影响的理由是可证的：提示条（`Toast.Provider`）被框架挂到 `<body>` 下，抽屉 / 弹窗走 React Aria 的模态覆盖层（也在 `<body>` 下），历史版本面板被有意放在容器外。**将来若在这些容器里直接挂 fixed 浮层，会踩同一个坑**。

## 4. 替代方案与为何不选（Alternatives）

| 方案 | 为什么不选 |
|---|---|
| 全站只做窗口媒体查询 | 同一窗口宽度下侧栏开合会改变内容区宽度，「窗口 1024 但内容区 780」时会让错栏；ADR 001 §2.3 的问题正是把窗口宽当成了可用宽 |
| 全站只做容器查询 | 侧栏是内容区的兄弟节点，量不到；浮层需要视口定位（§2.3） |
| 手机上另做一套页面/路由 | 与「小改为主」冲突，且两份结构必然漂移；本票要的是同一套结构弹性让位 |
| 历史版本改成整屏 Modal | 会把「编排与历史并排看」的能力在窄屏彻底砍掉，与 ADR 005 §2.5 冲突 |
