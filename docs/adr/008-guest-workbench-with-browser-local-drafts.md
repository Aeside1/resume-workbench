# ADR 008: 未登录先进工作台，游客态由浏览器本地草稿承载

- **状态（Status）**：Accepted（已确认）
- **日期（Date）**：2026-10-22
- **决策者（Deciders）**：用户 & AI Pair
- **关联文档**：[CONTEXT.md](../CONTEXT.md)、[ADR 002](002-retire-workspaces-flatten-to-user.md)、[ADR 005](005-resume-plan-reference-model-and-archive-boundary.md)、issue #12

---

## 1. 背景与问题陈述（Context）

当前实现把「认证」当成整个应用的入口闸门：`frontend/src/App.tsx` 里 `session ? <WorkbenchShell/> : <AuthPage/>`，没有 `localStorage['resume-session']` 就只能看登录页；`backend/app/dependencies.py` 的 `current_user` 对无令牌请求一律 401。用户因此提出：

> 改造登录验证，让未登录也能进入工作台查看和简单使用

issue #12 的原始需求意向里留下了四个必须先行定案的空白：

1. **未登录能做什么**：只读查看？能建本地草稿？还是只看示例数据？
2. **与 `docs/CONTEXT.md`「账号即工作台」的口径冲突**：是否要动领域模型（`ADR 002` 刚把工作区拍平到 user）。
3. **隐私边界**：工作台数据全部属于登录用户，未登录不可能读到真实数据，「查看」看到的是什么。
4. **认证链路现状**：`backend/app/auth_routes.py` + 前端 `AuthPage` / `resume-session` localStorage。

本 ADR 一次回答这四条，并把「游客态」明确为**前端本地体验态**，不动服务端数据模型。

## 2. 决策要点（Decisions）

### 2.1 认证不再是入口闸门，默认落地态是游客工作台

- `App` 不再用「有没有 session」决定渲染登录页还是工作台：**没有 session 时直接渲染游客工作台**。
- 认证页降级为一条**按需路由**：侧栏底部与游客横幅上的「登录 / 注册」进入 `AuthPage`，`AuthPage` 提供「先以游客身份继续」返回游客态。
- 登录成功后进入账号工作台（`WorkbenchShell` + 服务端数据源），退出登录回到游客态，而不是回到登录页。

### 2.2 游客工作台不是「第二个工作区」，也不引入 User

`ADR 002` 的结论（账号即唯一工作空间、不引入 Workspace/租户）**不变**。游客工作台（Guest Workspace）定义为：

> **未登录访客在这台浏览器里试写经历资产时使用的本地草稿域；它没有服务端身份，不是 User，也不是账号内的第二个工作区。**

- 它不是一张表、不是一个 `user_id`，服务端完全不知道它存在。
- 它不改变 `docs/CONTEXT.md` 的关系拓扑（`User → ExperienceGroup → ...`）：领域模型描述的是**账号工作台**；游客态是同一套对象形状在浏览器里的临时副本。
- 一旦登录，工作台回到账号域，读写都走服务端；本地草稿不再参与（迁移见 §2.7）。

### 2.3 可写范围：经历资产可读可写，简历方案保留为账号能力

| 能力 | 游客态 | 理由 |
|---|---|---|
| 浏览工作台外壳、工作台概览、经历内容列表 | 可 | 「进入工作台查看」的底线 |
| 经历分组 / 具体工作内容 / 简历亮点的创建、编辑、归档、恢复、彻底删除 | 可（写本地） | 「简单使用」＝真的能记下内容并看到沉淀效果，而不是只读样例 |
| 载入示例内容 / 清空本地草稿 | 可 | 让「查看」有内容可看，也让试写可以随时归零 |
| 简历方案（组合、编排、文稿、留档） | **需登录** | 方案的语义是「一次求职准备的组合 + 不可变留档」，留档与读时装配是服务端能力（ADR 005）；游客态不提供组合输出，避免做出一个登录后必然丢失的假能力 |

简历方案入口在游客态显示为登录引导面板，而不是隐藏入口——用户要先知道这块能力存在，才知道登录能换来什么。

### 2.4 隐私边界：游客态不向业务接口发任何请求

- 未登录时 `api` 层按 token 分派到**浏览器本地后端**，业务请求一个都不出网；因此不存在「读到他人数据」的面。
- 展示用的样例内容由前端内置静态样例（不来自数据库），命名以「示例」开头，横幅明确说明是示例数据，可一键清空。
- 服务端鉴权口径不变：无 `Authorization` 头一律 401；本 ADR 不改任何后端路由。

### 2.5 落实方式：`api` 按 token 分派数据源，组件签名不变

- `frontend/src/api.ts` 拆成 `httpBackend(token)` 与 `guestBackend()` 两个实现，`api.*(token, ...)` 按 token 分派；`GUEST_TOKEN` 定义在 `frontend/src/session.ts`。
- 组件继续接收 `session: Session`，游客 Session 为 `{ token: GUEST_TOKEN, user: { id: 0, email: '游客模式' } }`。这样画布、抽屉、列表等现有工作面**零改动**即可在游客态跑通；`isGuestSession()` 只用于外壳层的身份展示与能力门禁。
- 本地草稿落在 `localStorage['resume-guest-workspace']`（版本化 JSON，读写都做防御性解析），失效或损坏一律视为空草稿。

### 2.6 游客态的可见提示

- 顶层横幅（侧栏之外、内容区之上）写明「游客模式：数据只保存在这台浏览器」，并提供「登录 / 注册」「载入示例内容」「清空本地草稿」。
- 侧栏身份名片在游客态显示「游客工作台 / 本地草稿 · 未登录」，底部按钮由「退出登录」换成「登录 / 注册」。
- 工作台概览标题在游客态显示「游客工作台」而不是邮箱。

### 2.7 本地草稿的生命周期（明确不做什么）

- 本地草稿只存在这台浏览器的 `localStorage` 里：换设备、清站点数据、换浏览器都不会带过去，UI 必须如实告知（横幅文案）。
- **本切片不做「登录后把本地草稿导入账号」**：跨域迁移涉及去重、合并冲突与失败回滚，属于独立设计（已另开 issue [#13](https://github.com/Aeside1/resume-workbench/issues/13) 跟踪）。因此文案不承诺自动同步。
- 退出登录回到游客态时，之前那批本地草稿仍在（同一浏览器），用户可以继续试写或清空。

## 3. 结果与影响（Consequences）

- **收益**：
  - 首次访问即可看到工作台的真实形状并动手试写，「账号即工作台」不再意味着「先交出邮箱才能看一眼」；
  - 服务端零改动：没有新增匿名用户、影子账号或跨用户数据面，隐私与鉴权口径完全保持；
  - 组件签名不变，游客态复用全部既有编辑能力，实现面集中在一个本地后端 + 外壳门禁。
- **代价与风险**：
  - 前端多出一套与 `ExperienceGroupService` / `ResumeDescriptionService` 对齐的本地实现，两边行为可能漂移 → 用测试锁住关键语义（新建位置递增、归档过滤、删除级联、亮点默认标签）；
  - 「本地草稿」是易失数据，用户可能误以为是云端 → 横幅与侧栏必须常驻提示，并在迁移能力落地前不承诺同步；
  - 认证页不再是默认页面，`App.test.tsx` 里「进入登录页」的既有断言改为先点「登录 / 注册」。

## 4. 与既有决策的关系

- **ADR 002（扁平化到 user）**：继续有效。本文不新增工作区概念，游客工作台没有服务端身份。
- **ADR 005（引用模型与留档边界）**：继续有效。简历方案的读时装配与写时留档仍是服务端能力，因此游客态不提供。
- **ADR 003（HeroUI 单一 token 主题）**：新增的横幅与门禁面板只使用 HeroUI 组件与语义变量，不写死明暗色值、不使用 Emoji。

## 5. 验收口径（可测）

1. 无 `resume-session` 首次访问：直接进入工作台，能看到「游客模式」横幅与经历分组列表，不出现登录表单。
2. 游客新建经历分组 → 进入画布 → 新增具体工作内容 → 新增简历亮点，全部成功；刷新页面后仍在（`localStorage`）。
3. 游客访问「简历方案」：显示登录引导，不渲染方案列表，也不发任何 `/api/resume-plans` 请求。
4. 游客点「登录 / 注册」可进入认证页，并能「先以游客身份继续」返回游客工作台。
5. 登录后：横幅与游客身份消失，读写走服务端；退出登录回到游客态。
6. 「载入示例内容」写入带「示例」前缀的经历分组与亮点；「清空本地草稿」后回到空状态。
