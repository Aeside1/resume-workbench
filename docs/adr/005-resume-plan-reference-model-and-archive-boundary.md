# ADR 005: 简历方案的引用模型、预览/留档边界与「组合—投递」分离

## 1. 背景与问题陈述（Context）

核心闭环切片 04「简历方案」动手前的设计评审（`grill-with-docs`，2026-09-14）暴露出四个此前被含糊带过的问题，它们互相耦合，任何一个单独拍都会给后面的切片留下返工：

1. **「简历描述」名不副实**：它今天只是 `work_contents.supplementary_notes` 这个文本列里的一段 JSON，`id` 由浏览器生成（时间戳），服务端对其无任何语义。方案要「引用」它时，引用的是一串浏览器本地才唯一的字符串——换设备、清缓存、导入导出都会让已排好的方案找不到来源。
2. **「版本」一词双关**：它同时被用来指「面向不同岗位的几版简历」与「同一条描述被改过几次」。前者是组合层（简历方案），后者是资产层（描述自身的修订），混在一起导致「历史」「回滚」这些词无法判断作用对象。
3. **预览与快照谁负责落库**：PRD NFR-02 要求预览与导出共用同一份组装结果，05 又要做「创建后不可变的导出快照」。如果预览也存一份，就会出现两套「存下来的方案」。
4. **「组合之上还要改」没有着落**：用户明确表达过——组合出简历后，实际投递时还需要在结果上增删板块、改措辞。这个「再编辑」发生在哪一层，此前从未定义；若直接让方案本身可自由编辑，引用就会失去意义。

此外评审确认了与既有 ADR 的两处关系：ADR 002 已废除 `Workspace`，但 spec §4 的 API 路径仍写着 `/api/workspaces/:id/...`；ADR 003 §6 曾把描述抽屉定为**模态**抽屉，而方案编辑器需要「边看预览边操作」的非模态侧栏。

## 2. 决策要点（Decisions）

### 2.1 简历描述独立成表，引用存双列

- 新增 `resume_descriptions` 表：`id`、`work_content_id`、`label`、`content`、`position`、`archived`、时间戳。它是「同一件事的不同写法」的宿主，有稳定的服务端 id。
- **不使用 PostgreSQL 数组列**。理由有三条硬约束：① PG 不支持数组元素到标量列的外键，数组里的 id 可以是悬空值，而「被引用就不许删」正依赖该约束（报错形态见 [PG 数组文档](https://www.postgresql.org/docs/current/arrays.html) 与 [dba.stackexchange 讨论](https://dba.stackexchange.com/questions/126893/foreign-key-for-array-column)）；② PG 官方文档明确劝阻把数组当集合使用（"Arrays are not sets; searching for specific array elements can be a sign of database misdesign."），「反查这条亮点被哪些方案引用」用表是一次索引查询，用数组是全文扫描；③ 方案条目不只装一个编号——它还带所属经历块与排序位置，数组塞不下。
- `WorkContent` → `ResumeDescription` 是一对多，只需在描述表上放归属列，**不需要中间表**；`ResumePlan` → `ResumeDescription` 是多对多且每条连接自带结构与顺序，承载它的 `plan_items` 表本身就是领域对象「简历条目」，不是为规范化额外维护的关系表。
- 简历条目**同时保存** `work_content_id` 与 `resume_description_id`。冗余存 `work_content_id` 的价值：写入时可做纯行内校验（亮点必须属于该工作内容，否则 422），读取组装时少一次 join。
- 存量数据（`supplementary_notes` 中的三种历史形状：`{note,versions}`、`{note,descriptions[{points}]}`、裸数组/纯文本）由**幂等的** `backend/migrate_003_*.sql` 展开成行，命令与前后行数核对记入 `README.md`。旧 JSON 保留为只读兼容，`note` 字段继续留在原列（它不属于描述域）。

### 2.2 「组合」是引用，「再编辑」不由本模块承接

- 简历方案**只保存引用**（经历块 + 条目），绝不保存组合结果的文本副本。切换亮点只改引用。
- 「在组合之上自由编辑」的诉求**不通过让方案可编辑来满足**，而是：把组合结果组装为**通用 Markdown 文稿**并允许下载，作为交付给「投递稿」阶段的输入。
- **范围界定**：投递稿的编辑与渲染（含富文本排版、个人信息 / 教育 / 技能等非工作内容板块）**不属于简历组合模块的实现范围**，本切片不实现、不为其保存任何字段。它的归属——本应用内的独立模块，还是应用外工具——**留待后续单独设计，不在本 ADR 内假定**。
- 由此产生的边界收益：切片 04 不必处理排版与通用简历板块（PRD §12 待确认问题 5 因此不阻塞本切片），只需保证 Markdown 文稿这一种交换格式稳定。

### 2.3 预览读时组装，留档才是写时快照

- 简历方案的组装是一个**纯读时函数**：读取方案 → 经历块 → 条目 → 亮点 → 工作内容，产出结构化大纲与 Markdown 文本。方案编辑器的中栏编排视图与「下载文稿」共用该函数，结果不落库。
- **方案留档（`plan_archives`）是唯一的写时快照**，`source` 区分两类：`revision`（结构性变更自动追加，供回滚）与 `export`（导出动作追加，即导出快照）。两者共用一张表，避免「方案历史」与「导出历史」各存一份、用户不知道该回滚到哪一份。
- 留档创建后不可变，回滚 = 把方案恢复到那一版并**追加一条新的 `revision` 留档**（历史本身只增不改）。
- 05 的导出快照在此模型下只是「`source=export` 的留档 + 投递备注 + 下载与只读查看」，**不新增存储模型**。

### 2.4 归档与删除的守卫口径

- **归档不阻断已有引用**：已归档的经历分组 / 工作内容 / 亮点不再出现在「添加」候选中，但已有条目继续引用并在文稿中正常输出（归档的语义是「暂不使用」，不是「作废已有简历」）。引用解析不到时渲染为显式的「引用已失效」条目，绝不静默丢弃。
- **删除被引用的资产被拒绝**：彻底删除正被任何方案引用的经历分组 / 工作内容 / 亮点时返回 409，响应体列出引用它的方案名称（对应 UI-UX §7「说明受影响的简历方案和引用关系」）。**明确否决「自动回落到第一条描述」**：简历内容在用户不知情时被替换，是投递材料中最不可接受的失败模式。

### 2.5 界面口径

- 简历方案编辑器采用**两栏**：主工作面（简历编排，占满剩余宽度）+ 右侧**可收起的非模态**面板（历史版本回滚）。
- 右侧面板**不是模态覆盖层**：不设遮罩、不阻塞主工作面。这不推翻 ADR 003 §6——经历资产页的「简历亮点提炼」抽屉仍是 HeroUI 原生模态抽屉（各自服务不同场景），本 ADR 只是为方案编辑器**新增**一条非模态约定。
- 领域词汇以 CONTEXT.md 为准：面向用户的正式名是 **简历亮点**（不再叫「版本」「描述版本」）、**简历大纲 / 板块 / 经历块 / 简历条目**、**方案留档 / 简历文稿 / 投递稿**；代码标识符 `ResumeDescription` 等保留旧名。

## 3. 决策影响（Consequences）

**正面：**

- 方案对亮点的引用有数据库级完整性保证，「被引用就不许删」「被哪些方案引用」都变成可执行查询；
- 「组合（共享资产）」与「投递（个人稿）」彻底分离，本切片不需要做富文本排版，边界不会随需求漂移；投递稿阶段放在何处（应用内新模块或应用外工具）不被本 ADR 提前钉死；
- 只有一处「写时快照」（留档表），05 不需要第二套存储模型，NFR-02 由「共用组装函数」保证而非靠约定；
- 「版本」双关被拆解，「历史」「回滚」的作用对象在术语层就唯一了。

**负面 / 代价：**

- 必须写并执行一次性数据搬运脚本（开发库现有 19 条工作内容、其中 6 条带描述 JSON，含两种旧形状），脚本必须幂等且可重复执行；
- 新增三张业务表 + 一张留档表，且**没有版本化迁移机制**（无 Alembic）——本轮沿用 `create_all` + 手写幂等 SQL，该技术债已在 spec §9 登记；
- 已被引用的资产不能直接删除，用户需先移除引用；UI 必须把 409 的原因说清楚，否则会被感知为「删不掉」；
- 乐观并发（spec 原 §7）仍未实现，本轮明确不做并降级登记。

## 4. 与既有 ADR 的关系

- **ADR 002（扁平化至用户账号）**：本 ADR 沿用其结论。spec §4 中残留的 `/api/workspaces/:id/...` 路径口径由本次评审修正为用户作用域直挂。
- **ADR 003（HeroUI 原生视觉与单一 Token）**：本 ADR 不推翻其任何决策。§2.5 为非模态侧栏新增约定，与 §6 记录的模态描述抽屉并存。
- **ADR 004（Zen 非模态区域展开）**：本 ADR §2.5 沿用其「非模态区域展开优于浮层覆盖」的思路，属同一设计倾向在方案编辑器上的复用。
